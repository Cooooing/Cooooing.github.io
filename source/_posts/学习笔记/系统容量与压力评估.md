## 什么是系统可承受的压力

“系统能承受多少 QPS”不是一个可以脱离条件回答的问题。同一个接口在缓存命中和未命中、返回几十字节和返回数 MB 数据、读数据库和写数据库、单机和多实例部署时，能达到的吞吐量都不同。

更准确的定义是：**在给定的流量模型、数据规模、部署环境和服务目标下，系统能够持续处理请求，同时满足延迟、错误率与业务正确性要求的最大负载。**

这里有四个不能省略的条件：

1. **流量模型**：请求速率是稳定的还是突发的；读写比例、请求体大小、热点分布分别是什么。
2. **服务目标**：例如“P99 延迟不高于 300 ms，5xx 错误率不高于 0.1%”。没有目标，无法判断某个负载下的表现是否合格。
3. **持续时间**：短时间跑到 10,000 QPS 不代表能够持续承载。内存泄漏、队列积压、连接池耗尽和磁盘写入常常需要更长时间才会暴露。
4. **依赖边界**：应用、数据库、缓存、消息队列和第三方服务共同决定容量。入口服务还有余量，不表示整条请求链路仍有余量。

因此，容量结论应写成类似下面的形式：

> 在 4 个相同应用实例、MySQL 读写分离、缓存命中率约 95%、商品详情读请求占 90% 的条件下，系统以 3,000 QPS 稳态运行 30 分钟时，P99 延迟为 180 ms，5xx 错误率低于 0.05%，数据库连接池等待时间未持续增长。

这个结论可以复验，也明确了它不适用于哪些条件。

## 评估容量时需要看的指标

### 吞吐量：单位时间完成了多少工作

吞吐量表示单位时间内系统完成的工作数量。常见单位如下：

| 指标 | 含义 | 适用对象 |
| --- | --- | --- |
| QPS / RPS | 每秒查询数 / 请求数 | HTTP、RPC、搜索接口 |
| TPS | 每秒完成的事务数 | 支付、下单等有完整事务边界的业务 |
| 消费速率 | 每秒消费的消息数 | Kafka、RabbitMQ、任务队列 |
| 写入速率 | 每秒写入的记录、字节或事件数 | 数据库、日志、时序库 |
| 网络吞吐 | 每秒传输的字节数 | 网关、文件服务、流媒体服务 |

QPS 只计数请求，不说明请求是否成功，也不说明响应是否及时。例如入口收到 10,000 QPS，但其中 3,000 个请求超时，或者全部请求只是在队列中等待，都不能称为系统已经“承受住了 10,000 QPS”。因此吞吐量必须和错误率、延迟、积压一起观察。

平均 QPS 的计算为：

$$
\text{QPS} = \frac{\text{时间窗口内完成的请求数}}{\text{窗口时长（秒）}}
$$

例如 60 秒内完成 12,000 个请求，平均 QPS 为 200。窗口越大，曲线越平滑，但越容易掩盖尖峰；窗口越小，越容易发现瞬时波动，但噪声更大。监控中通常同时保留短窗口和长窗口的速率视图。

### 延迟：请求花了多长时间

延迟必须使用分位数，而不能只看平均值。假设 100 个请求中 99 个耗时 10 ms，1 个耗时 10 s：平均值约为 110 ms，看上去尚可；但那一个请求的用户实际等待了 10 秒。

| 指标 | 含义 | 适合回答的问题 |
| --- | --- | --- |
| 平均值（Average） | 总耗时除以请求数 | 总体资源成本大致如何 |
| P50 | 50% 请求不超过该耗时 | 普通用户的典型体验 |
| P90 / P95 | 90% / 95% 请求不超过该耗时 | 较慢请求是否正在增加 |
| P99 | 99% 请求不超过该耗时 | 长尾延迟是否满足服务目标 |
| 最大值 | 窗口内最慢请求 | 排查线索，不适合作为稳定 SLA |

需要先明确测量位置。客户端总耗时、网关耗时、应用处理耗时、数据库执行耗时不是同一个指标。一个 HTTP 请求的总时间可以近似拆为：

```text
客户端排队 + 网络传输 + 网关排队 + 应用排队 + 应用处理
          + 下游调用等待 + 下游处理 + 响应传输
```

应用只记录业务函数耗时，无法发现请求在连接池或工作队列中等待了多久；只看客户端耗时，又无法直接定位慢在何处。需要用指标和链路追踪将这些阶段区分开。

### 错误与正确性：请求是否得到正确结果

错误率通常按状态码、错误类型或业务结果分别统计：

$$
\text{错误率} = \frac{\text{失败请求数}}{\text{总请求数}} \times 100\%
$$

至少应区分：

- 4xx：参数、鉴权、限流等客户端或策略问题；
- 5xx：服务端处理失败；
- 超时：调用方在期限内没有收到结果；
- 取消：客户端主动中断，或上游 context 被取消；
- 业务失败：例如库存不足、状态不允许流转。这不一定是系统故障，但可能是业务流量变化的重要信号；
- 重试：应单独计数。重试会增加实际进入系统的请求量，不能混入正常业务吞吐。

“返回 200”也不必然代表业务正确。例如异步任务已入队但消费者持续积压、数据库主从复制延迟导致读到旧数据，都可能让 HTTP 请求成功而业务目标尚未完成。对关键流程还应观测最终状态、补偿次数和一致性校验结果。

### 并发、排队与饱和度：系统是否开始堆积

并发数是某一时刻正在处理或等待处理的请求数。它与连接数、goroutine 数、线程数不同：一个请求可能占用连接但未执行，也可能在队列中等待而尚未获得工作线程。

饱和度描述资源或队列是否接近极限。常见信号包括：

| 位置 | 需要观测的饱和信号 |
| --- | --- |
| CPU | 使用率持续接近可用核数；运行队列变长 |
| 内存 | 堆持续增长、频繁 GC、接近容器内存限制、发生 OOM |
| 连接池 | 已用连接接近上限、等待连接的请求数和等待时间增长 |
| 工作池 | 活跃 worker 达上限、任务队列长度持续增长 |
| 消息队列 | producer 速率持续高于 consumer 速率、consumer lag 增长 |
| 数据库 | 慢查询增加、锁等待增加、活跃连接满、磁盘 I/O 等待升高 |
| 网络 | 带宽接近上限、重传增加、连接建连失败增加 |

队列长度只在持续增长时才说明系统处理能力低于到达速率。短暂尖峰后队列回落，属于缓冲吸收流量；队列持续上升则意味着延迟会不断恶化，最终表现为超时、拒绝或内存耗尽。

## 指标之间如何互相约束

### Little 定律：并发、吞吐量和延迟

在稳定系统中，Little 定律给出平均在系统中的请求数、到达速率与平均停留时间的关系：

$$
L = \lambda W
$$

- $L$：系统中的平均请求数，也可近似理解为平均并发；
- $\lambda$：平均到达速率，例如 QPS；
- $W$：请求从进入系统到离开系统的平均时间。

假设接口稳定处理 500 QPS，端到端平均耗时为 200 ms（0.2 秒），则平均有：

$$
L = 500 \times 0.2 = 100
$$

个请求处于系统中。

它不是容量公式，而是检查指标是否自洽的工具。若 QPS 基本不变、处理时间从 200 ms 上升到 2 s，系统内并发请求理论上会从约 100 增长到约 1,000；如果工作池或连接池容量远小于这个数字，请求就会在队列中等待，延迟进一步升高。

Little 定律依赖稳定状态下的平均值，不能直接用 P99 替换平均耗时，也不能用于请求无限堆积的系统。它仍能帮助发现一个常见事实：**延迟上升会占用更多并发容量；更多排队又会继续推高延迟。**

### 带宽与数据量

网络容量常被 QPS 掩盖。若平均每个请求和响应合计 100 KB，1,000 QPS 对应的有效载荷约为：

$$
1{,}000 \times 100\ \text{KB/s} \approx 100\ \text{MB/s}
$$

这还没有计算 TCP/IP、TLS、HTTP 头部和重传开销。响应体变为 1 MB 后，即使 QPS 不变，带宽需求也增加十倍。文件下载、批量接口和日志上报服务，应同时以请求数与字节速率作为容量指标。

### 重试放大与级联故障

设上游每秒发起 1,000 次调用，其中 20% 因超时重试一次，则下游实际收到的调用数约为：

$$
1{,}000 + 1{,}000 \times 20\% = 1{,}200\ \text{QPS}
$$

如果请求可重试两次、多个服务都各自重试，放大倍数会更高。下游变慢时，盲目重试会让它收到更多请求，进一步恶化超时；这就是为什么超时、重试、限流、熔断和退避必须作为一组机制设计。

观测时至少分开记录“首次请求”和“重试请求”，并在压测模型中包含真实的超时与重试策略。否则入口 QPS 看似正常，但依赖服务可能已经被重试流量压垮。

### 最慢依赖决定端到端容量

一次请求经过网关、应用、缓存、数据库和第三方服务时，任何一个关键依赖达到饱和都可能限制整条链路。应用实例 CPU 只有 40% 并不表示系统还有 60% 的容量：瓶颈可能是数据库连接池、缓存热点分片、下游接口配额，或单个序列化锁。

容量评估需要沿调用链找出最早达到阈值的资源，并记录它达到阈值时的流量、延迟和错误率。扩容非瓶颈层通常无法提高总容量，反而可能向瓶颈发出更多并发请求。

## 从目标到压测结果

### 先定义服务目标和负载模型

压测不是“把并发调到最大”。开始前应定义目标，例如：

| 项目 | 示例 |
| --- | --- |
| 被测接口 | `GET /api/products/{id}`、`POST /api/orders` |
| 流量比例 | 商品详情 80%，下单 15%，取消订单 5% |
| 数据规模 | 100 万商品、10 万活跃用户、热点商品占 20% 请求 |
| 请求模型 | 稳态 1,000 QPS，5 分钟后升至 2,000 QPS；每 10 分钟一次 3,000 QPS 突刺 |
| 延迟目标 | 读接口 P99 < 200 ms；写接口 P99 < 500 ms |
| 错误目标 | 5xx < 0.1%，超时 < 0.05% |
| 持续时间 | 稳态至少 30 分钟；长稳测试至少数小时 |

压测数据必须接近生产的大小和分布。空数据库、小数据集、全部命中缓存或永远使用同一个 ID，都会让结论偏乐观。涉及写入时还要考虑索引增长、事务日志、清理任务和缓存失效后的表现。

### 常见压测模型

| 模型 | 做法 | 用途 |
| --- | --- | --- |
| 基线测试 | 小负载下运行 | 确认测试链路和正常延迟 |
| 阶梯加压 | 每隔固定时间增加 QPS 或并发 | 找到延迟、错误或饱和度的拐点 |
| 稳态压测 | 固定目标负载持续运行 | 验证目标容量是否可持续 |
| 突刺压测 | 短时间快速提高流量 | 验证队列、限流和弹性扩容行为 |
| 长稳压测 | 长时间运行 | 暴露泄漏、积压、连接泄漏和周期性任务问题 |
| 故障压测 | 注入延迟、错误或实例故障 | 验证超时、重试、熔断和降级是否有效 |

还需区分**开环**和**闭环**模型。开环压测按预定速率持续发出请求，适合模拟外部流量持续到达；闭环压测由固定数量的虚拟用户在收到响应后再发起下一次请求，负载会随响应变慢而自动下降。用闭环模型时，系统越慢，压测工具实际发出的请求可能越少，容易掩盖过载；报告中必须说明模型。

### 何时认为达到容量边界

不要只在 CPU 达到 100% 时才认为测试结束。以下任一现象持续出现，都意味着已越过当前目标容量：

- P95、P99 延迟在增加负载后突然上升，且降载后才回落；
- 错误率、超时率或限流拒绝率超过服务目标；
- 消息积压、连接池等待或工作队列长度持续增长；
- 某项关键资源持续打满，例如数据库连接、缓存分片、磁盘 I/O；
- 重试请求比例持续增加；
- 关键业务校验失败，例如重复扣减、订单状态异常或数据不一致。

报告中不要只写“最高达到 5,000 QPS”。应记录达到该负载时的分位延迟、错误率、资源水位、测试持续时间、瓶颈位置和降级策略是否触发。

## 建立观测体系

### 指标、日志、追踪与剖析

四类信号解决不同问题：

| 信号 | 适合回答的问题 | 常见内容 |
| --- | --- | --- |
| Metrics | 系统是否正在变慢、变错或变满 | QPS、延迟直方图、错误计数、CPU、连接池等待 |
| Logs | 某个失败请求发生了什么 | 错误栈、参数摘要、状态码、请求 ID |
| Traces | 一次请求慢在调用链的哪里 | Span 耗时、下游调用、排队、重试 |
| Profiles | 进程为什么消耗 CPU、内存或发生阻塞 | CPU、堆、goroutine、mutex、block profile |

它们需要能关联起来。例如网关把 request ID 或 trace ID 传递给下游；指标按路由、状态码和服务名聚合；日志携带 trace ID。发生 P99 上升时，先从指标确认是哪些接口和实例受影响，再从追踪定位慢调用，最后通过日志和 profile 分析根因。

### Golden Signals、RED 与 USE

Google SRE 书籍中的四个黄金信号是：

- **Latency**：服务请求耗时；
- **Traffic**：服务处理的需求量；
- **Errors**：失败请求比例或数量；
- **Saturation**：最受限资源的饱和程度。

它适合从服务整体判断是否健康。对于请求驱动的服务，还可用 RED 方法组织指标：

| RED | 含义 | 典型指标 |
| --- | --- | --- |
| Rate | 请求速率 | `http_requests_total` 的增长速率 |
| Errors | 错误数或错误率 | 5xx、超时、RPC error |
| Duration | 请求耗时 | 延迟直方图、P95/P99 |

对于 CPU、磁盘、网络接口、数据库连接池等资源，USE 方法更合适：

| USE | 含义 | 示例 |
| --- | --- | --- |
| Utilization | 资源忙碌比例 | CPU 使用率、连接池已用比例 |
| Saturation | 等待该资源的工作量 | 运行队列、连接池等待数、磁盘队列长度 |
| Errors | 资源错误 | 磁盘错误、连接失败、网络丢包 |

CPU 使用率高是 Utilization；等待 CPU 调度的任务增加才是 Saturation。二者一起观察，才能判断是需要扩容、优化热点代码，还是瓶颈其实在别处。

### Prometheus 指标设计

Prometheus 常用三类指标：

| 类型 | 用途 | 例子 |
| --- | --- | --- |
| Counter | 只增不减的累计事件数 | 请求总数、错误总数、重试总数 |
| Gauge | 可升可降的瞬时值 | goroutine 数、连接池当前占用、队列长度 |
| Histogram | 观测值分布 | HTTP 耗时、响应大小、数据库查询耗时 |

HTTP 指标通常至少包含请求 Counter 与耗时 Histogram。标签应能回答“哪个接口、哪种方法、什么状态结果导致变化”，但不能携带无限变化的值。

适合的标签：`service`、`route`、`method`、`status_code`、`operation`。

不适合的标签：`user_id`、`request_id`、完整 URL、完整错误文本、订单号、IP 地址。它们会产生高基数时间序列，导致 Prometheus 内存和查询压力明显上升。路径应使用路由模板如 `/api/orders/{id}`，而不是实际 URL。

在 PromQL 中，可以通过：

~~~promql
# 最近 5 分钟每秒请求数，按路由和状态码聚合
sum by (route, status_code) (
  rate(http_server_requests_total[5m])
)

# 最近 5 分钟某路由的 P99 延迟
histogram_quantile(
  0.99,
  sum by (le, route) (
    rate(http_server_request_duration_seconds_bucket[5m])
  )
)
~~~

`rate()` 适合展示一段时间内的平滑速率；窗口不能小于抓取间隔的数倍，否则结果容易波动或缺样本。分位数应从直方图 bucket 计算，不应先在每个实例上计算分位数再平均，因为平均后的结果不再代表整体 P99。

## Go 服务中的基础观测

Go 标准库 `runtime/metrics` 提供运行时指标，`net/http/pprof` 可以导出 CPU、堆、goroutine、mutex、block 等 profile。应用层请求指标通常通过 Prometheus Go client 或 OpenTelemetry SDK 暴露。

下面示例用 `prometheus/client_golang` 为 HTTP 服务记录请求总数和处理耗时。实际项目中应尽量从路由框架取得**路由模板**，而不是直接使用原始 URL 路径。

~~~go
package main

import (
    "net/http"
    "strconv"
    "time"

    "github.com/prometheus/client_golang/prometheus"
    "github.com/prometheus/client_golang/prometheus/promhttp"
)

var (
    requestsTotal = prometheus.NewCounterVec(
        prometheus.CounterOpts{
            Name: "http_server_requests_total",
            Help: "Total number of HTTP requests handled by the server.",
        },
        []string{"route", "method", "status_code"},
    )

    requestDuration = prometheus.NewHistogramVec(
        prometheus.HistogramOpts{
            Name:    "http_server_request_duration_seconds",
            Help:    "HTTP request processing duration in seconds.",
            Buckets: []float64{0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5},
        },
        []string{"route", "method"},
    )
)

func init() {
    prometheus.MustRegister(requestsTotal, requestDuration)
}

type statusRecorder struct {
    http.ResponseWriter
    statusCode int
}

func (w *statusRecorder) WriteHeader(code int) {
    w.statusCode = code
    w.ResponseWriter.WriteHeader(code)
}

func metrics(route string, next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        recorder := &statusRecorder{ResponseWriter: w, statusCode: http.StatusOK}
        startedAt := time.Now()

        next.ServeHTTP(recorder, r)

        labels := []string{route, r.Method}
        requestDuration.WithLabelValues(labels...).Observe(time.Since(startedAt).Seconds())
        requestsTotal.WithLabelValues(append(labels, strconv.Itoa(recorder.statusCode))...).Inc()
    })
}

func main() {
    mux := http.NewServeMux()
    mux.Handle("GET /api/products/{id}", metrics("/api/products/{id}", http.HandlerFunc(productHandler)))
    mux.Handle("GET /metrics", promhttp.Handler())

    _ = http.ListenAndServe(":8080", mux)
}

func productHandler(w http.ResponseWriter, r *http.Request) {
    w.Header().Set("Content-Type", "application/json")
    _, _ = w.Write([]byte(`{"id":"demo","name":"product"}`))
}
~~~

这个示例有几个边界：

- 它记录的是 handler 执行时间，不包含客户端到服务端的网络耗时，也不包含请求到达 handler 前的网关排队。
- 若 handler 直接调用 `Write` 而不调用 `WriteHeader`，记录器默认的 200 状态码仍正确；若需要兼容 `http.Flusher`、`http.Hijacker` 等可选接口，应使用更完整的包装实现或框架中间件。
- Histogram bucket 应按照服务目标和实际延迟范围配置。若 P99 目标是 300 ms，0.25、0.5 等相邻 bucket 才能提供足够的估算精度。
- 路由、方法、状态码的基数通常可控；不要加入用户 ID、订单 ID 或原始 URL。

对于性能问题，profile 比单纯的业务指标更接近根因。开发环境可在独立管理端口开启 `net/http/pprof`，再用 `go tool pprof` 采集和分析：

~~~go
import _ "net/http/pprof"

go func() {
    // 仅在受访问控制的管理地址暴露，不能直接开放到公网。
    _ = http.ListenAndServe("127.0.0.1:6060", nil)
}()
~~~

~~~shell
# 采集 30 秒 CPU profile
go tool pprof http://127.0.0.1:6060/debug/pprof/profile?seconds=30

# 查看 goroutine 堆栈
go tool pprof http://127.0.0.1:6060/debug/pprof/goroutine
~~~

CPU profile 用于定位计算热点；heap profile 用于分析内存占用；mutex 和 block profile 可辅助发现锁竞争与阻塞。profile 会带来一定开销，也可能暴露函数名、调用栈和业务信息，应限制访问范围，并避免在未经评估的高压生产环境中长时间采集。

## 总结

容量不是“跑出了多少 QPS”，而是在明确流量模型和服务目标后，系统持续提供正确服务的能力。吞吐量、延迟分位数、错误率、并发与队列饱和度共同描述这个能力；任何单一指标都不足以说明系统是否健康。

实践时应先定义目标和流量模型，再通过阶梯加压与长稳压测寻找瓶颈；生产中用 Metrics 发现趋势、用 Trace 定位调用链、用 Logs 还原失败上下文、用 Profile 分析进程内部原因。容量结论必须包含环境、数据分布、持续时间和瓶颈条件，才能成为后续扩容与优化的可靠依据。
