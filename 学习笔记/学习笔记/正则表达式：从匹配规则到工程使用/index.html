正则表达式解决什么问题

正则表达式（regular expression，常写作 regex 或 regexp）是一种描述字符串模式的语言。程序将模式交给正则引擎，再由引擎判断输入中是否存在符合模式的片段，或者提取、替换这些片段。

常见用途包括：

  • 从日志中提取时间、请求 ID、IP 地址等结构化字段；
  • 检查用户名、编号、日期等文本是否符合预期格式；
  • 批量替换文本中的固定结构；
  • 按规则切分字符串。

正则表达式描述的是字符结构，不是业务事实。例如，\d{4}-\d{2}-\d{2} 可以匹配 2026-99-99，却不能证明这是一个有效日期；匹配电子邮件的常见模式也不能证明邮箱存在、归属某人或可以收信。格式检查之外的语义，应由日期库、数据库、验证码或其他业务规则完成。

从模式到匹配结果

正则表达式由字面量、元字符、字符类、锚点、量词、分组和选择组成。引擎在输入中寻找满足整个模式的一段文本；是否要求覆盖整个输入、字符类如何解释、某些扩展语法是否支持，取决于模式和所用引擎。

本节是一份通用速查表，适合学习和编写模式时查询。不同引擎对 Unicode、锚点、命名分组、断言等细节可能不同；这些差异应在目标语言或工具的文档中确认。

匹配范围与位置

目标 推荐模式 说明
查找任意位置的数字 \d+ 可在 A-1024 中找到 1024
整个输入都是数字 ^\d+$ ^、$ 限制匹配覆盖整个输入
以 http:// 或 https:// 开头 ^https?:// ? 表示前一元素出现零或一次
单独的单词 cat \bcat\b \b 是单词边界；对中文分词通常无效
每一行以 ERROR: 开头的文本 (?m)^ERROR:.*$ 多行模式下，^、$ 匹配行的起止位置

锚点不匹配实际字符，只限制模式出现的位置。

模式 常见含义
^ 输入开头；多行模式下通常也表示行首
$ 输入结尾；多行模式下通常也表示行尾
\A 输入绝对开头；并非所有引擎支持
\z 输入绝对结尾；并非所有引擎支持
\b 单词边界
\B 非单词边界

完整校验通常写作 ^模式$。但 $ 是否允许匹配最后一个换行符之前的位置、\b 如何定义单词字符，都可能因引擎而异；需要严格校验时，应以实际引擎的规则为准。

字面量、转义与字符类

普通字符匹配自身，例如 cat 匹配连续的 cat。.、*、+、?、(、)、[、]、{、}、|、^、$、\ 等是元字符；若要匹配它们自身，通常需要使用反斜杠转义。

目标文本 正则模式 说明
a.b a\.b . 默认匹配一个字符，\. 匹配句点
a+b a\+b + 是量词，\+ 匹配加号
a(b) a\(b\) 圆括号默认用于分组
C:\temp C:\\temp 字面量反斜杠通常写成 \\
任意一个字符 . 多数引擎默认不匹配换行符
换行、制表符、回车 \n、\t、\r 匹配对应控制字符
十六进制字符 \x7F 匹配十六进制编码对应字符
一段纯字面量文本 \Q[a-z]+\E 支持该语法的引擎中，内部元字符失去特殊含义

字符类 [] 一次匹配一个字符。[] 中的 ^ 只有位于开头时表示取反；连字符 - 通常用于范围，若要匹配连字符本身，可将它放在首尾或转义为 \-。

模式 匹配内容
[abc] a、b、c 中任意一个
[^abc] 除 a、b、c 外的任意一个字符
[a-z] 一个小写 ASCII 字母
[A-Za-z0-9_] 一个大小写 ASCII 字母、数字或下划线
[0-9A-Fa-f] 一个十六进制数字
[-a-z]、[a-z-] 小写 ASCII 字母或连字符
\d、\D 一个数字 / 一个非数字字符
\s、\S 一个空白字符 / 一个非空白字符
\w、\W 一个单词字符 / 一个非单词字符
[[:alpha:]] 一个 ASCII 字母（POSIX 字符类）
[[:digit:]] 一个 ASCII 数字（POSIX 字符类）
\p{Han} 一个汉字字符（支持 Unicode 属性的引擎中）
\P{Han} 一个非汉字字符（支持 Unicode 属性的引擎中）
\p{L}、\p{Lu} 任意 Unicode 字母 / 大写 Unicode 字母

\d、\s、\w 以及 \p{...} 的精确定义存在引擎差异。需要精确限制格式时，使用显式字符范围，例如 [0-9]、[A-Za-z]，通常更清楚。

量词、选择与分组

量词修饰前一个原子；原子可以是字符、字符类、转义序列或一个分组。下表量词行中的 x 是占位符，表示“前一个原子”，不是固定要匹配的字母 x。例如 a* 表示字母 a 出现零次或多次，\d+ 表示数字字符类出现一次或多次，(ab){2} 表示整体 ab 出现两次。

写法 含义 示例
x* x 出现零次或多次 空串、x、xxx
x+ x 出现一次或多次 x、xxx
x? x 出现零次或一次 空串、x
x{n} x 恰好出现 n 次 x{3} 匹配 xxx
x{n,} x 至少出现 n 次 x{2,} 匹配 xx、xxx
x{n,m} x 出现 n 至 m 次 x{2,4} 匹配 xx 至 xxxx
x*?、x+?、x?? 对应量词的懒惰形式 尽可能少匹配，但仍使整体成功
a|b 匹配 a 或 b GET|POST 匹配 GET 或 POST
(re) 捕获组：匹配 re 并保存其结果 (ab)+ 将 ab 作为整体重复
(?:re) 非捕获组：只分组，不保存结果 (?:GET|POST) /api；并非所有引擎支持
(?<name>re)、(?P<name>re) 命名捕获组 语法与支持范围因引擎而异

ab+ 只重复 b；要重复整个 ab，应写 (ab)+。竖线 | 表示“或”；圆括号用于将多个元素组成整体，也可以保存匹配结果。

选择的范围由分组决定：GET|POST /api 表示 GET，或 POST /api；(GET|POST) /api 才表示 GET /api 或 POST /api。

量词默认通常是贪婪的：<.*> 用于 <b>一</b><i>二</i> 时，通常会匹配到最后一个 >；<.*?> 则会依次匹配四个标签。比起依赖贪婪或懒惰量词，按数据边界排除字符往往更可靠，例如 <[^>]*>。

正则表达式适合描述局部、扁平的文本结构，不适合解析任意 HTML、XML、JSON 或编程语言源码。这些格式具有嵌套结构、转义规则或上下文语义，应使用对应解析器。

修饰符与高级语法

修饰符（flag）会改变后续模式或局部子模式的解释方式。写法和支持范围因引擎而异。

写法 常见作用
i 或 (?i) 忽略大小写
m 或 (?m) 多行模式，^、$ 匹配行边界
s 或 (?s) dotall 模式，. 可以匹配换行符
U 或 (?U) 交换贪婪与懒惰量词的默认行为；并非所有引擎支持
(?i:re) 仅对 re 启用忽略大小写
(?-i)、(?im-s:re) 关闭或组合局部修饰符；引擎支持情况不同

以下是编写模式时常见、但不具备完全通用性的高级语法：

能力 常见写法 用途
回溯引用 (\w+)\s+\1 匹配重复出现的同一文本
前瞻 \d+(?=px) 要求后方满足条件，但不消耗后方文本
后顾 (?<=#)\w+ 要求前方满足条件，但不消耗前方文本
条件分支 (?(1)a|b) 根据某个分组是否匹配选择分支
原子组 (?>re) 禁止该组内部回溯
递归匹配 (?R) 用于部分嵌套结构；并非解析器的替代品

这些语法在不同引擎中的支持和行为差异很大。使用前应确认目标语言或工具的文档，而不应仅以在线正则工具的结果为准。

在 Go 中使用 regexp 包

RE2 语法特征与限制

Go 的 regexp 包使用 RE2 引擎。修饰符写在模式内，可作用于剩余模式，也可以限制在一个分组内。

写法 作用
(?i)、(?i:re) 忽略大小写；后者仅作用于 re
(?m)、(?m:re) 多行模式，^、$ 匹配行边界
(?s)、(?s:re) dotall 模式，. 可以匹配换行符
(?U)、(?U:re) 非贪婪模式，交换贪婪与懒惰量词的默认行为
(?-i)、(?im-s:re) 关闭一个修饰符，或在分组内组合设置

RE2 为保证线性时间匹配，明确不支持下列常见扩展：

不支持的能力 常见写法 替代方向
回溯引用 (\w+)\s+\1 提取两段文本后在 Go 代码中比较
前瞻 \d+(?=px) 先匹配候选文本，再检查后缀
后顾 (?<=#)\w+ 匹配 #(\w+) 后提取捕获组
条件分支、原子组 (?(1)a|b)、(?>re) 拆为普通 Go 控制流
分支重置、递归匹配 (?|...)、(?R) 改用多个模式或解析器

除上述语法差异外，RE2 的匹配语义与常见回溯型引擎也不完全相同；跨语言迁移模式时，应使用目标语言的引擎文档重新验证。

编译与转义

API 用途 失败行为
regexp.Compile(expr) 编译动态或需要处理错误的模式 返回 (*Regexp, error)
regexp.MustCompile(expr) 编译代码中固定且已测试的模式 编译失败时 panic
regexp.CompilePOSIX(expr) 按 POSIX 左最长规则编译 返回 (*Regexp, error)
regexp.MustCompilePOSIX(expr) 编译固定的 POSIX 模式 编译失败时 panic
regexp.QuoteMeta(text) 将普通文本转为可安全嵌入模式的字面量 不编译模式

Go 推荐使用原始字符串 `...` 编写固定模式，例如 `^\d+$` 会原样传给正则引擎。若使用双引号字符串，则还需处理 Go 字符串转义，相同模式写作 "^\\d+$"。

这里 QuoteMeta 防止 userInput 中的 .、*、[ 等字符改变模式含义。它只用于模式，不用于 ReplaceAllString 的替换字符串。CompilePOSIX 使用 POSIX 左最长规则；通常的 Compile 使用左端最先匹配规则。普通模式如无明确要求，使用 Compile 即可。

匹配、查找与索引

包级 regexp.MatchString(pattern, text) 会每次编译 pattern，适合一次性使用。已有 *Regexp 时使用下表方法。

这些匹配 API 都采用“查找是否存在匹配子串”的语义。若要校验整个输入，模式必须显式使用 ^、$，例如 ^\d+$；\d+ 仍会在 订单 A-1024 中匹配到 1024。

包级函数 输入类型 用途
regexp.Match(pattern, b) []byte 一次性判断字节切片是否包含匹配
regexp.MatchString(pattern, s) string 一次性判断字符串是否包含匹配
regexp.MatchReader(pattern, r) io.RuneReader 一次性判断字符流是否包含匹配
方法 返回内容 未匹配时
re.MatchString(s) 是否存在匹配子串 false
re.FindString(s) 第一个匹配子串 ""
re.FindStringIndex(s) 第一个匹配的字节区间 [start, end] nil
re.FindAllString(s, n) 最多 n 个匹配；n < 0 表示全部 nil
re.FindAllStringIndex(s, n) 多个匹配的字节区间 nil
re.Split(s, n) 按匹配处切分字符串 由 n 控制结果数量

索引均以字节偏移量表示，不是 rune 个数。处理中文文本时，不能把 FindStringIndex 的返回值当作字符下标；可以用它直接切片 s[start:end]，或者按需将字符串转换为 []rune 后再处理。

以上字符串方法都有面向 []byte 的同名变体，例如 Find、FindIndex、FindAll、FindSubmatch、ReplaceAll。处理 io.RuneReader 时可使用 FindReaderIndex 和 FindReaderSubmatchIndex。除输入和返回类型外，匹配语义相同。

捕获组与替换

FindStringSubmatch 返回完整匹配和每个捕获组；FindStringSubmatchIndex 返回它们的字节区间。具名分组可配合 SubexpNames、SubexpIndex 避免依赖难读的数字下标。

方法 用途
re.NumSubexp() 捕获组数量，不包括完整匹配
re.SubexpNames() 与编号对应的分组名称；未命名项为空字符串
re.SubexpIndex(name) 获取命名组编号；不存在时返回 -1
re.FindStringSubmatch(s) 第一个完整匹配和各捕获组文本
re.FindStringSubmatchIndex(s) 第一个完整匹配和各捕获组字节区间
re.FindAllStringSubmatch(s, n) 多个匹配及其各捕获组
re.ReplaceAllString(s, repl) 用替换模板替换所有匹配
re.ReplaceAllStringFunc(s, func) 对每个匹配调用函数生成替换结果
re.ReplaceAllLiteralString(s, repl) 将 repl 视为字面量，不展开 $1、${name}
re.ExpandString(dst, template, src, match) 根据匹配索引将替换模板展开到 dst
re.LiteralPrefix() 返回可确定的字面量前缀及其是否覆盖整个模式
re.Longest() 将该 Regexp 切换为左最长匹配；不应与并发匹配同时调用

替换方法中的 $1、${name} 引用捕获组。ReplaceAllLiteralString 会将替换文本原样写入；ReplaceAllStringFunc 直接接收每个匹配文本并返回替换结果，适合执行计算或安全地插入外部文本。

性能与边界

Go 的 RE2 保证匹配时间相对输入长度是线性的，因此传统回溯型引擎中 (a+)+、(.*)* 引发的灾难性回溯不会发生。但这不代表可忽略资源限制：超长输入、收集全部匹配、复杂替换和频繁编译模式仍会消耗 CPU 或内存。

  • 为外部输入设置长度上限；
  • 只需要一个结果时使用 FindString，不要无条件使用 FindAllString(..., -1)；
  • 固定模式预编译并复用；
  • 不接受不可信来源提供的任意正则表达式作为模式；
  • 对日期、URL、邮箱、标识符等格式匹配成功后，继续完成相应的语义校验。

总结

正则表达式的关键不在于记住所有符号，而在于先定义匹配目标和边界：是查找片段还是校验整体，哪些字符允许出现，哪些字段需要提取，哪些语义必须交给后续代码验证。

处理真实业务文本时，保持模式短小、测试充分，理解 Go RE2 的语法边界，并把不可信动态模式排除在输入路径之外。正则表达式适合描述局部、扁平的文本规则；当数据有递归嵌套或复杂语义时，解析器和结构化校验通常是更合适的工具。
